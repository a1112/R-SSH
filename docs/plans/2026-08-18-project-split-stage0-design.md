# Project Split Stage 0 Diagnostics Design

**Date:** 2026-08-18
**Status:** Approved
**Scope:** Stage 0 measurement contract only

## Context

R-SSH cannot safely begin the physical repository split until it has a trustworthy,
cross-platform way to measure the startup and steady-state costs of the current
monolith. The existing SSH GUI startup harness is useful, but it is Windows-specific,
couples measurement to PowerShell, reports process-private memory through `sysinfo`,
and covers only the first-present path.

Stage 0 establishes a stable observation boundary before later stages change crate,
runtime, renderer, and repository ownership. Its output is a versioned diagnostic
record that can be compared before and after each split stage.

## Goals

Stage 0 will provide:

1. A reusable `rssh-diagnostics` library for marker parsing, schema validation,
   statistics, process sampling, and structured failures.
2. A native `rssh-bench-launcher` executable that owns process launch, readiness,
   stabilization, sampling, teardown, and JSON output.
3. Cross-platform child-process memory measurements:
   - Windows: Private Working Set.
   - Linux: proportional set size (PSS).
   - macOS: physical footprint (`phys_footprint`).
4. Two deterministic GUI scenarios:
   - `empty-window`: a rendered window with no local PTY and no SSH transport.
   - `ssh1`: one native SSH pane connected to an isolated loopback fixture, with a
     visible connection prompt/state proving readiness.
5. A unified schema containing startup milestones and steady-state samples.
6. Fixed-runner collection with 5 warmups and 30 process-cold samples.
7. Shared-runner functional coverage without absolute performance gating.

## Non-goals

Stage 0 does not:

- Rename existing crates.
- Move runtime or renderer code between crates or repositories.
- Remove the current PowerShell startup contract until parity is proven.
- Optimize startup or memory usage.
- Make the proposed 45 MiB and 60 MiB steady-state budgets blocking immediately.
- Benchmark SFTP, SCP, forwarding, multiple SSH panes, local PTYs, 4K, or non-default
  DPI configurations.

## Architecture

The new crate is a measurement boundary, not an application dependency inversion:

```text
crates/rssh-diagnostics/
  Cargo.toml
  src/
    lib.rs
    schema.rs
    marker.rs
    statistics.rs
    sampler.rs
    sampler/
      windows.rs
      linux.rs
      macos.rs
    bin/
      rssh-bench-launcher.rs
```

Responsibilities are deliberately separated:

- The GUI emits timestamped lifecycle markers and exposes a bounded benchmark hold
  mode. It does not inspect its own memory or calculate statistics.
- `rssh-bench-launcher` launches exactly one child application, reads markers,
  enforces deadlines, samples that child only, tears it down, and emits one result.
- `rssh-diagnostics` defines the schema and performs platform-neutral validation and
  aggregation.
- Platform sampler modules translate native operating-system measurements into the
  unified byte-valued schema.
- The isolated loopback SSH fixture remains test-owned and provides deterministic
  authentication and host-key material.

This boundary is intended to survive later project splitting: the launcher consumes
an executable and a marker protocol, not internal GUI types.

## Launcher Interface

The initial public command is:

```text
rssh-bench-launcher \
  --app <path-to-rssh> \
  --scenario empty-window|ssh1 \
  --stabilization-ms 5000 \
  --sample-interval-ms 100 \
  --sample-count 10 \
  --json
```

Additional arguments required to run `ssh1` are passed as explicit fixture metadata
or generated by the runner. Secrets are never accepted as ordinary launcher command
line values and never enter markers or the result schema.

The launcher must reject zero durations/counts, an absent app executable, unsupported
scenario/platform combinations, and unknown trailing arguments. Defaults match the
command above.

## Scenario Contract

### Empty window

The application creates an 80 x 24 window at a benchmark-only 100% scale, produces a
non-empty CPU first frame, and remains alive for sampling. It must not start a local
PTY, native SSH connection, configuration watcher, or unrelated background transport.
Deferred configuration and GPU initialization may run because they are part of the
real hybrid startup path.

Readiness is the first successful presentation. GPU readiness is observed separately
and may happen later or not at all.

### One SSH pane

The application creates one 80 x 24 SSH GUI pane and connects to a deterministic
loopback native SSH server. The fixture owns its host key and authentication identity;
ambient OpenSSH configuration, agent state, and user home files are excluded.

Readiness requires both:

1. A successful window presentation.
2. A visible, non-secret connection state or prompt associated with the SSH pane.

The steady-state sampling window begins only after the pane reaches the scenario's
declared ready state. Any test password or private-key passphrase is provided through
an isolated secret channel and is searched for in stdout, stderr, session logs,
markers, and JSON output.

## Timing Model

The launcher records monotonic durations relative to a process-start boundary. The
schema uses descriptive milestone names rather than relying on a fixed T0-T7 array:

- `process_started_ms` is always `0` in a completed run.
- `window_created_ms` is optional when the application fails earlier.
- `first_present_ms` is the first successful present boundary.
- `config_ready_ms` is optional for a benchmark that exits before configuration.
- `transport_started_ms` is optional for `empty-window`.
- `transport_ready_ms` is optional for `empty-window` and required for successful
  `ssh1`.
- `gpu_ready_ms` is optional and is allowed to be later than `first_present_ms`.
- `scenario_ready_ms` is the readiness boundary used before stabilization.
- `sampling_started_ms` and `sampling_finished_ms` bound the sample series.
- `process_exited_ms` records natural or launcher-requested termination.

The hybrid renderer correction is intentional: CPU presentation can make the window
interactive before GPU initialization completes. Validators must not require
`gpu_ready_ms <= first_present_ms`, nor treat an absent GPU milestone as failure when
the final renderer is CPU.

The marker timestamp is captured at the observed event boundary. Expensive memory
queries and JSON serialization occur afterward and must not change milestone timing.

## Marker Protocol

Markers are newline-delimited JSON written to stdout with an explicit prefix so they
can coexist with ordinary diagnostics. Each marker includes:

- schema version;
- run identifier;
- process identifier;
- scenario;
- marker kind;
- monotonic elapsed milliseconds;
- marker-specific structured fields.

Markers are flushed immediately. The parser:

- ignores non-marker stdout lines;
- rejects malformed prefixed records;
- rejects a schema/run/PID/scenario mismatch;
- accepts optional milestones and renderer fallback;
- rejects duplicate terminal markers and decreasing timestamps;
- preserves unknown fields for forward-compatible diagnostics.

## Schema v2

The top-level result is versioned as `rssh.diagnostics/v2` and contains:

```text
schema
run
  id
  scenario
  platform
  architecture
  app_path
  app_version
  started_at_utc
  launcher_version
configuration
  stabilization_ms
  sample_interval_ms
  sample_count
  dimensions
  scale_factor
milestones
readiness
  status
  evidence
renderer
  first
  final
connection
  final_state
memory
  metric
  unit
  samples
  statistics
process
  pid
  exit_kind
  exit_code
  teardown_ms
failures
```

Memory sample values are unsigned bytes and carry a metric discriminator:

- `windows_private_working_set_bytes`
- `linux_pss_bytes`
- `macos_phys_footprint_bytes`

Statistics include `count`, `min`, `max`, `mean`, `median`, `p50`, and `p95`. Percentile
selection uses nearest-rank semantics and is tested at empty, singleton, even, odd,
and repeated-value boundaries. A successful result contains exactly the configured
sample count.

The schema does not pretend that the three platform metrics are numerically
equivalent. They share storage and reporting shape so trends can be compared within a
platform and fixed runner.

## Native Memory Samplers

### Windows

The sampler opens the child PID with query rights and obtains
`PROCESS_MEMORY_COUNTERS_EX2`. It reports `PrivateWorkingSetSize` when supported. If
the API or field is unavailable, the run fails with an explicit unsupported or
sampling error; it must not silently substitute Private Bytes, Working Set, or
`sysinfo::virtual_memory()`.

### Linux

The sampler reads `/proc/<pid>/smaps_rollup` and parses the `Pss:` value in KiB. If
`smaps_rollup` is unavailable, the initial version reports unsupported rather than
silently falling back to RSS. Integer conversion to bytes is checked for overflow.

### macOS

The sampler calls the supported task/process information API that exposes physical
footprint and reports `phys_footprint`. Permission denial, process exit, and API
unavailability remain distinct failures. RSS is not an accepted substitute.

### Common behavior

Every sampler:

- is created for one PID and never follows descendants;
- confirms the target process still refers to the launched child where the platform
  exposes an identity token;
- performs no recursive process-tree aggregation;
- returns typed errors for not found, access denied, unsupported, malformed native
  response, overflow, and transient sampling failure;
- never converts failure to a zero sample.

## Sampling State Machine

```text
Launch
  -> AwaitMarkers
  -> AwaitScenarioReady
  -> Stabilize(5 s default)
  -> Sample(100 ms x 10 default)
  -> RequestShutdown
  -> Reap
  -> EmitResult
```

Every state has an explicit deadline. Child exit before the expected state produces a
structured failure containing the last valid marker and bounded stdout/stderr tails.
Launcher-requested shutdown is graceful first, then forceful within a bounded cleanup
deadline. The launcher never leaves a benchmark child or loopback fixture detached.

## Failure Model

Failures are data, not only exit text. Each failure includes:

- stable code;
- phase (`launch`, `marker`, `readiness`, `stabilization`, `sampling`, `shutdown`, or
  `fixture`);
- human-readable message;
- optional OS error code;
- recoverability classification;
- bounded diagnostic context.

Examples include `app_not_found`, `marker_timeout`, `marker_protocol`,
`scenario_not_ready`, `sampler_unsupported`, `sampler_access_denied`,
`sample_count_mismatch`, `child_exited_early`, `fixture_failed`, and
`cleanup_deadline`.

JSON is emitted even for a completed diagnostic failure when the launcher itself can
serialize a result. The process exit code remains non-zero for failed runs.

## CI and Rollout

Shared pull-request runners execute deterministic tests only:

- schema and marker parsing;
- state-machine deadlines with fake clocks/processes;
- statistics;
- platform parser/API seam tests;
- empty-window functional smoke where supported;
- loopback fixture contract without absolute budgets.

The protected fixed release runner executes each scenario with 5 warmups and 30
process-cold measurements. It archives all per-run v2 JSON plus an aggregate summary.

The existing first-present contract remains blocking:

- first-present p95 <= 500 ms;
- its existing first-frame memory contract remains unchanged during migration.

New Stage 0 steady-state observations are initially report-only:

- empty window target: 45 MiB;
- one SSH pane target: 60 MiB.

They become blocking only after enough fixed-runner history proves the sampler and
variance envelope. A missing or invalid Stage 0 result is still a functional failure;
only the numeric steady-state threshold is report-only.

## Security and Privacy

- Passwords and passphrases never appear in command lines, markers, JSON, logs, or
  snapshot evidence.
- Output tails are bounded and redacted before serialization.
- The SSH fixture binds loopback only and accepts only its generated identity.
- The launcher inherits the minimum environment required by the scenario and records
  no environment values.
- Result paths and process arguments are diagnostic metadata only when known not to
  contain secrets.

## Testing Strategy

Implementation follows test-driven batches:

1. Schema, marker parser, validation state machine, and statistics.
2. Windows, Linux, and macOS sampler seams plus platform-specific integration probes.
3. GUI benchmark marker and bounded hold behavior for empty-window and SSH scenarios.
4. Deterministic loopback SSH orchestration and secret-leak scans.
5. Runner scripts, fixed/shared CI contracts, documentation, and migration parity.

Tests use fake clocks and scripted process/sampler ports wherever wall-clock timing is
not the subject. Native probes are feature/platform gated and bounded.

## Acceptance Criteria

Stage 0 is complete when:

1. `rssh-bench-launcher` can produce valid v2 JSON for `empty-window` and `ssh1` on a
   supported fixed runner.
2. Windows reports Private Working Set, Linux reports PSS, and macOS reports physical
   footprint without semantic fallback.
3. Each successful run contains the configured number of child-only samples after
   readiness and stabilization.
4. Startup milestones correctly represent the CPU-first/GPU-later hybrid path.
5. Fixture and application cleanup are bounded and leave no owned process alive.
6. Secret scans find zero occurrences in every observable artifact.
7. Shared CI runs functional contracts; fixed CI runs 5 warmups and 30 cold samples
   and archives results.
8. Existing first-present gates remain green and the new 45/60 MiB observations are
   reported without blocking releases.

Success means the project has a credible, repeatable measurement contract for later
split stages. It does not mean the target memory values have already been achieved.
